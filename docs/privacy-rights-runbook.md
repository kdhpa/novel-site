# 개인정보 권리 요청 운영 절차

이 절차는 계정 정지, 로그인 장애, 이메일 공급자 장애 등으로 `/settings`의 데이터 내보내기·계정 삭제를 직접 사용할 수 없는 요청자를 위한 운영 경로입니다.

## 운영 전 준비

- `NEXT_PUBLIC_PRIVACY_CONTACT`에는 담당자가 실제로 확인하는 이메일 주소 또는 HTTPS 요청 페이지를 설정합니다. 프로덕션에서 누락되거나 형식이 잘못되면 `/api/health`가 unhealthy를 반환합니다.
- 개인정보 요청은 일반 고객지원 티켓과 분리하고 최소 권한 담당자만 접근하게 합니다.
- 접수, 본인 확인, 승인, 전달·삭제 완료 시각을 케이스 ID로 기록하되 비밀번호, 인증 토큰, 전체 원고를 티켓 본문에 복사하지 않습니다.

## 처리 절차

1. 요청 종류(열람·정정·삭제·처리 제한), 계정 이메일, 회신 채널을 접수하고 7일 이내 접수 사실과 다음 단계를 안내합니다.
2. DB의 현재 계정 이메일과 검증 상태를 최소 조회로 확인합니다. 요청자에게 비밀번호나 OAuth 토큰을 요구하지 않습니다.
3. 자동 인증 메일이 활성화된 경우 등록된 검증 이메일로 단일 사용·짧은 만료의 확인 링크를 보내 소유권을 확인합니다. 자동 메일이 비활성화된 경우 담당자가 개인정보 문의 메일함에서 등록 이메일로 케이스별 무작위 확인 문구를 보내고, 같은 메일함에서 그 문구가 포함된 회신을 받아 소유권을 확인합니다. 발신자 주소만 보고 확인을 끝내지 않습니다.
4. 자동 인증 메일이 활성화된 활성 계정은 `/settings`의 10분 단일 사용 토큰과, credentials 계정인 경우 현재 비밀번호를 사용하는 self-service 흐름으로 안내합니다. 자동 메일이 비활성화되었거나 이메일 접근이 불가능하면 담당자 두 명이 본인 확인 근거와 처리 범위를 승인하고 기록합니다. 불필요한 신분증 사본은 수집하지 않습니다.
5. 수동 요청과 정지 계정은 일반 서비스 접근을 임의로 복구하지 않습니다. 권한 있는 개인정보 담당자가 검토된 일회성 작업으로 `apps/web/src/app/api/user/export/route.ts`의 allowlist와 동일한 필드만 추출하거나, 계정 삭제 서비스 로직과 동일한 cascade·스토리지 정리를 수행합니다. 승인된 실행 도구가 준비되지 않은 경우 원시 SQL로 대체하지 말고 보안 검토가 가능한 엔지니어링 작업으로 에스컬레이션합니다. 원시 DB dump나 관리자 감사 metadata 전체를 전달하지 않습니다.
6. 암호화된 전달 채널과 별도 키 교환으로 결과를 제공하고 임시 파일을 즉시 파기합니다. 삭제는 백업 순환 기간과 제한 보존되는 신고·감사 원문의 범위를 함께 알립니다.
7. 본인 확인 완료 후 30일 이내 처리를 내부 목표로 하며, 지연되면 사유와 새 일정을 먼저 안내합니다. 완료 뒤 케이스에는 결과와 승인자만 남기고 불필요한 증빙을 삭제합니다.

## 금지 사항

- 정지 사용자를 편의상 장시간 해제하거나 일반 서비스 접근을 열지 않습니다.
- 이메일 발신자 주소만 보고 본인 확인을 완료하지 않습니다.
- 신고 대상 원문, 다른 사용자의 식별자, 관리자 메모를 데이터 사본에 포함하지 않습니다.
- 실패한 작업을 성공으로 기록하거나 migration·DB 제약을 우회해 직접 삭제하지 않습니다.

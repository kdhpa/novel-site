# 캐릭터 챗봇 개발 계획

## 문서 상태

- 상태: 계획
- 대상: NovelVerse 웹 앱
- 목적: 작품에 등록된 캐릭터 설정을 이용해 독자가 캐릭터와 1:1로 대화할 수 있는 기능을 단계적으로 구축한다.
- 기본 원칙: 공개 승인된 작품의 캐릭터만 노출하고, 작가가 캐릭터별로 챗봇 사용을 명시적으로 허용한다.

## 1. 현재 기반

현재 `Character` 모델에는 다음 정보가 있다.

- 이름
- 캐릭터 설명
- 외형
- 성격
- 작품 내 역할
- 초상화와 초상화 프롬프트

이 정보는 캐릭터의 기본 정체성과 시각적 표현에는 충분하지만, 일관된 대화를 만들기 위해서는 말투, 첫 인사, 현재 상황, 행동 원칙, 지식 범위, 예시 대화가 추가로 필요하다.

현재 프로젝트에는 다음 기반도 마련되어 있다.

- NextAuth 기반 로그인과 사용자 권한
- 작품의 공개 및 승인 상태
- 작가와 관리자만 접근할 수 있는 캐릭터 관리 API
- Gemini 기반 텍스트 AI 호출 코드
- 캐릭터 초상화와 작품 이미지 생성 기능

Replicate는 이미지 생성에 계속 사용하고, 캐릭터 대화는 기존 Gemini 연결을 우선 활용한다. 대화 모델은 나중에 교체할 수 있도록 공급자별 구현을 분리한다.

## 2. 제품 원칙

1. 작품이 `isPublished = true`이고 `approvalStatus = APPROVED`인 경우만 독자에게 챗봇을 공개한다.
2. 공개 작품이라도 작가가 해당 캐릭터의 챗봇을 활성화하지 않으면 대화할 수 없다.
3. 캐릭터 설정은 서버에서 시스템 프롬프트로 조립하며 클라이언트가 임의로 변경할 수 없다.
4. 독자의 대화 기록은 해당 독자만 볼 수 있다.
5. 작가는 독자의 대화 원문을 볼 수 없다.
6. 관리자는 신고 처리 등 운영상 필요한 경우에만 관련 대화를 확인한다.
7. 비공개 원고, 미승인 회차, 독자가 아직 읽지 않은 회차의 정보는 대화에 사용하지 않는다.
8. 대화 비용과 응답 지연을 관리할 수 있도록 사용량과 실패율을 기록한다.

## 3. MVP 범위

### 포함

- 로그인 사용자의 1:1 텍스트 대화
- 캐릭터별 챗봇 활성화 설정
- 첫 인사와 캐릭터 말투 설정
- 실시간 스트리밍 응답
- 대화 목록과 대화 기록 저장
- 새 대화, 대화 삭제, 생성 중단, 답변 재생성
- 최근 대화 문맥 유지
- 긴 대화의 요약 기억
- 사용자별 메시지 사용량 제한
- 메시지 신고
- 작가용 챗봇 미리보기

### MVP에서 제외

- 여러 캐릭터가 동시에 참여하는 단체 대화
- 음성 대화
- 캐릭터가 이미지를 생성해 답변하는 기능
- 캐릭터 간 공유 기억
- 독자 간 공유 대화방
- 전체 회차를 대상으로 한 벡터 검색
- 유료 메시지 결제
- 복잡한 호감도 및 관계 시뮬레이션

## 4. 캐릭터 챗봇 설정

기존 `Character` 모델에 대화 필드를 계속 추가하지 않고, 1:1 관계의 `CharacterChatProfile` 모델을 별도로 둔다.

```prisma
model CharacterChatProfile {
  id               String   @id @default(cuid())
  characterId      String   @unique
  isEnabled        Boolean  @default(false)
  greeting         String   @db.Text
  speechStyle      String?  @db.Text
  scenario         String?  @db.Text
  worldview        String?  @db.Text
  boundaries       String?  @db.Text
  exampleDialogues Json?
  version          Int      @default(1)
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  character Character @relation(fields: [characterId], references: [id], onDelete: Cascade)
}
```

필드의 역할은 다음과 같다.

| 필드 | 용도 |
| --- | --- |
| `isEnabled` | 독자에게 챗봇을 노출할지 결정 |
| `greeting` | 새 대화에서 캐릭터가 보내는 첫 메시지 |
| `speechStyle` | 말투, 호칭, 문장 길이, 자주 쓰는 표현 |
| `scenario` | 캐릭터와 독자가 처음 만나는 상황 |
| `worldview` | 캐릭터가 알고 있는 세계관과 배경 정보 |
| `boundaries` | 캐릭터가 하지 않아야 할 행동과 답변 범위 |
| `exampleDialogues` | 말투 고정을 위한 사용자-캐릭터 예시 대화 |
| `version` | 캐릭터 설정 변경 시 대화 일관성을 관리하는 버전 |

캐릭터 설정을 수정하면 버전을 올린다. 기존 대화는 시작 당시 설정 스냅샷을 유지하고, 새 대화부터 최신 설정을 사용한다.

## 5. 대화 데이터 구조

### ChatConversation

한 사용자가 한 캐릭터와 진행하는 대화 단위다.

```prisma
model ChatConversation {
  id              String   @id @default(cuid())
  userId          String
  characterId     String
  title           String?
  summary         String?  @db.Text
  profileVersion  Int
  personaSnapshot Json
  status          String   @default("ACTIVE")
  lastMessageAt   DateTime @default(now())
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
}
```

`personaSnapshot`에는 대화 시작 당시의 캐릭터 이름, 성격, 역할, 말투, 시나리오, 지식 범위와 행동 원칙을 저장한다.

### ChatMessage

```prisma
model ChatMessage {
  id                String   @id @default(cuid())
  conversationId    String
  role              String
  content           String   @db.Text
  status            String   @default("COMPLETED")
  modelKey          String?
  promptTokens      Int?
  completionTokens  Int?
  providerRequestId String?
  errorCode         String?
  createdAt         DateTime @default(now())
}
```

`role`은 MVP에서 `USER`와 `ASSISTANT`만 저장한다. 시스템 프롬프트는 DB 메시지로 노출하지 않고 서버에서 매 요청마다 조립한다.

### ChatReport

신고 대상 메시지, 신고 사유, 처리 상태, 처리한 관리자와 처리 시간을 저장한다. 관리자 화면에서는 신고된 대화의 필요한 구간만 우선 노출한다.

## 6. 프롬프트 조립 순서

서버는 다음 순서로 대화 입력을 구성한다.

1. 서비스 공통 안전 정책
2. 캐릭터 설정 스냅샷
3. 공개 가능한 작품 소개와 세계관 정보
4. 이전 대화 요약
5. 최근 대화 메시지
6. 허용된 회차에서 검색한 참고 정보
7. 사용자의 새 메시지

중요한 규칙은 다음과 같다.

- 시스템 프롬프트와 캐릭터 설정은 클라이언트 입력보다 높은 우선순위를 갖는다.
- 작품 본문과 검색 결과는 신뢰할 수 없는 참고 자료로 구분해 프롬프트 명령으로 해석하지 않는다.
- 비공개 작품과 비공개 회차는 프롬프트에 포함하지 않는다.
- 사용자의 읽기 진행도보다 뒤의 회차는 기본적으로 검색하지 않는다.
- 캐릭터가 모르는 내용은 억지로 만들어내지 않고 캐릭터다운 방식으로 모른다고 답하도록 한다.

## 7. API 계획

### 독자용

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `GET` | `/api/chat/characters/[characterId]` | 대화 가능한 공개 캐릭터 정보 조회 |
| `GET` | `/api/chats` | 내 대화 목록 조회 |
| `POST` | `/api/chats` | 새 대화 생성 |
| `GET` | `/api/chats/[conversationId]` | 내 대화와 메시지 조회 |
| `DELETE` | `/api/chats/[conversationId]` | 대화 삭제 |
| `POST` | `/api/chats/[conversationId]/messages` | 사용자 메시지 저장 및 스트리밍 답변 생성 |
| `POST` | `/api/chats/[conversationId]/regenerate` | 마지막 캐릭터 답변 재생성 |
| `POST` | `/api/chat-messages/[messageId]/report` | 메시지 신고 |

### 작가용

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| `GET` | `/api/novels/[novelId]/characters/[characterId]/chat-profile` | 챗봇 설정 조회 |
| `PUT` | `/api/novels/[novelId]/characters/[characterId]/chat-profile` | 챗봇 설정 저장 및 버전 증가 |
| `POST` | `/api/novels/[novelId]/characters/[characterId]/chat-preview` | 공개하지 않고 작가가 시험 대화 |

모든 대화 API에서 사용자, 대화, 캐릭터, 작품의 관계를 서버에서 다시 검증한다. 클라이언트가 전달한 `userId`, 작가 권한 또는 공개 상태는 신뢰하지 않는다.

## 8. 화면 계획

### 작가 화면

캐릭터 편집 화면을 `기본 설정`과 `챗봇 설정`으로 나눈다.

챗봇 설정 화면에는 다음 항목을 둔다.

- 챗봇 공개 토글
- 첫 인사 입력
- 말투와 호칭 입력
- 대화 시작 상황 입력
- 세계관 지식 입력
- 금지 행동과 답변 범위 입력
- 예시 대화 편집
- 작가 전용 미리보기

작품이 미승인 상태면 설정과 미리보기는 가능하지만 독자 공개 토글은 실제 노출로 이어지지 않는다.

### 독자 화면

- 작품 상세의 캐릭터 목록에 `대화하기` 명령 추가
- `/chat/[characterId]`에서 새 대화를 시작하거나 최근 대화를 이어서 진행
- 데스크톱은 대화 목록과 본문을 나눈 작업형 화면
- 모바일은 대화 본문을 우선하는 전체 화면 구성
- 메시지 전송, 생성 중단, 재생성, 신고 메뉴 제공
- 캐릭터 초상화, 이름, 작품명을 상단에 고정
- 네트워크 오류와 생성 실패 시 작성한 사용자 메시지는 유지

### 관리자 화면

기존 비공개 운영 앱에 다음 기능을 추가한다.

- 신고 목록과 처리 상태
- 신고된 메시지의 전후 문맥 확인
- 사용자 및 캐릭터별 사용량
- 공급자 오류율과 평균 응답 시간
- 캐릭터 챗봇 비활성화 조치

## 9. AI 공급자 구조

대화 기능은 특정 모델 호출 코드에 직접 의존하지 않도록 한다.

```ts
interface ChatModelClient {
  streamMessage(input: ChatModelInput, signal: AbortSignal): AsyncIterable<string>;
  summarize(input: ChatSummaryInput): Promise<string>;
}
```

첫 구현은 `GeminiChatModelClient`로 진행한다. 모델 이름, 최대 출력 토큰, 온도와 타임아웃은 환경 변수 또는 서버 설정으로 관리한다.

응답 생성 정책은 다음과 같다.

- 첫 응답 조각부터 화면에 스트리밍한다.
- 사용자가 중단하면 `AbortController`로 공급자 요청을 취소한다.
- 스트리밍 시작 전 실패만 자동 재시도한다.
- 일부 답변이 전송된 뒤 실패하면 해당 메시지를 `FAILED`로 표시하고 재생성할 수 있게 한다.
- 동일 요청의 중복 저장을 막기 위해 요청 식별자를 사용한다.
- 대화가 일정 길이를 넘으면 오래된 메시지를 요약하고 최근 메시지만 모델에 전달한다.

## 10. 권한, 안전성과 개인정보

### 공개 조건

아래 조건을 모두 만족해야 독자가 대화를 시작할 수 있다.

```text
novel.isPublished = true
novel.approvalStatus = APPROVED
character.chatProfile.isEnabled = true
```

### 필수 보호 장치

- 로그인하지 않은 사용자의 대화 생성 차단
- 다른 사용자의 대화 ID 접근 차단
- 메시지 입력 길이 제한
- 사용자별 분당 및 일일 요청 제한
- 동시 생성 요청 제한
- 모델 응답 길이 제한
- 입력과 출력에 대한 안전성 검사
- 프롬프트 인젝션 방어
- 신고 및 관리자 차단 기능
- API 키와 시스템 프롬프트의 서버 전용 보관
- 대화 삭제 시 관련 메시지와 요약 삭제

작가에게는 대화 수, 평균 메시지 수 같은 집계 통계만 제공하고 독자별 대화 원문은 제공하지 않는다.

## 11. 사용량과 비용 관리

MVP에서는 다음 항목을 기록한다.

- 요청 사용자
- 캐릭터와 작품
- 사용 모델
- 입력 및 출력 토큰
- 응답 소요 시간
- 성공, 취소, 실패 상태
- 공급자 오류 코드

초기에는 계정별 무료 일일 한도를 설정값으로 관리한다. 실제 사용량이 확인된 뒤 무료 한도, 작가별 한도 또는 유료 기능을 결정한다.

원문 프롬프트 전체를 일반 오류 로그에 남기지 않는다. 운영 로그에는 요청 식별자와 상태를 기록하고, 신고 처리용 대화 데이터는 DB 권한을 통해 제한한다.

## 12. 작품 본문 지식 연동

이 단계는 MVP 안정화 이후 진행한다.

1. 공개된 회차의 HTML을 일반 텍스트로 정규화한다.
2. 회차 번호와 문단 위치를 보존한 작은 단위로 분할한다.
3. 검색용 임베딩을 생성해 PostgreSQL의 벡터 검색 기능에 저장한다.
4. 사용자 메시지와 관련된 조각만 대화 프롬프트에 추가한다.
5. 사용자의 읽기 기록을 기준으로 검색 가능한 최대 회차를 제한한다.
6. 회차 수정, 공개 취소 또는 삭제 시 검색 인덱스를 갱신한다.

벡터 검색을 도입하기 전에는 작품 소개와 작가가 직접 입력한 `worldview`만 사용한다. 전체 작품 본문을 매 요청마다 프롬프트에 넣지 않는다.

## 13. 단계별 구현 순서

### 0단계: 세부 정책 확정

예상 기간: 0.5일

- 로그인 필수 여부 확정
- 무료 일일 메시지 수 확정
- 대화 보관 기간 확정
- 허용할 콘텐츠 연령 기준 확정
- 캐릭터 챗봇 설정에 별도 관리자 승인이 필요한지 확정

### 1단계: 데이터와 작가 설정

예상 기간: 1~2일

- Prisma 모델과 마이그레이션 추가
- 챗봇 프로필 검증 스키마 추가
- 작가용 설정 API 추가
- 캐릭터 편집 화면에 챗봇 설정 추가
- 작가용 시험 대화 추가

### 2단계: 대화 백엔드

예상 기간: 2~3일

- 모델 공급자 인터페이스 추가
- Gemini 스트리밍 어댑터 추가
- 프롬프트 조립기 추가
- 대화 및 메시지 API 추가
- 생성 중단, 중복 방지, 실패 상태 처리
- 최근 메시지 문맥과 대화 요약 추가

### 3단계: 독자 채팅 화면

예상 기간: 2~3일

- 작품 상세에서 대화 진입점 추가
- 채팅 화면과 대화 목록 구현
- 스트리밍, 중단, 재생성, 삭제 구현
- 모바일과 데스크톱 화면 검증
- 로딩, 빈 상태, 오류 상태 구현

### 4단계: 운영과 안정화

예상 기간: 1~2일

- 요청 및 일일 사용량 제한
- 신고 API와 운영 화면
- 토큰 비용과 실패율 기록
- 권한 및 프롬프트 보안 테스트
- 핵심 흐름 E2E 테스트

### 5단계: 작품 지식과 장기 기억

예상 기간: 3~5일

- 공개 회차 인덱싱
- 스포일러 범위 적용
- 관련 문맥 검색
- 사용자별 장기 기억과 친밀도 설계
- 기억 조회 및 삭제 설정

MVP 예상 기간은 6~10 개발일이다. 작품 본문 검색과 장기 기억까지 포함하면 추가로 3~5 개발일을 예상한다.

## 14. 테스트 계획

### 단위 테스트

- 캐릭터 설정으로 올바른 시스템 프롬프트가 생성되는지 확인
- 비공개 필드가 공개 응답에 포함되지 않는지 확인
- 긴 대화가 정해진 토큰 예산 안에서 요약되는지 확인
- 캐릭터 설정 버전과 스냅샷 동작 확인

### API 통합 테스트

- 미로그인 사용자 차단
- 다른 사용자의 대화 접근 차단
- 미승인 작품과 비활성 캐릭터 차단
- 스트리밍 정상 완료, 취소, 공급자 실패 처리
- 중복 요청 시 메시지가 두 번 저장되지 않는지 확인
- 대화 삭제 시 하위 메시지도 삭제되는지 확인

### E2E 테스트

- 작가가 챗봇을 설정하고 미리보기하는 흐름
- 승인된 작품의 캐릭터만 독자에게 노출되는 흐름
- 독자가 새 대화를 시작하고 나중에 이어서 대화하는 흐름
- 모바일에서 입력창과 메시지가 겹치지 않는지 확인
- 관리자가 신고된 메시지를 처리하는 흐름

## 15. MVP 완료 기준

- 승인되고 공개된 작품의 활성화된 캐릭터만 대화 목록에 나타난다.
- 사용자는 캐릭터와 대화하고 새로고침 후에도 기록을 이어갈 수 있다.
- 답변은 스트리밍되며 중단과 재생성이 정상 동작한다.
- 캐릭터의 이름, 성격, 말투와 설정이 여러 응답에 걸쳐 유지된다.
- 다른 사용자의 대화에는 접근할 수 없다.
- 캐릭터 설정 변경이 기존 대화를 예기치 않게 바꾸지 않는다.
- 요청 한도와 사용량 기록이 동작한다.
- 신고된 메시지를 비공개 운영 화면에서 처리할 수 있다.
- 미승인 작품과 비공개 회차의 내용이 모델에 전달되지 않는다.

## 16. 이후 확장 후보

- 사용자와 캐릭터의 친밀도 및 관계 단계
- 캐릭터가 기억할 정보를 사용자가 직접 확인하고 삭제하는 기능
- 작품의 특정 시점이나 상황을 선택하는 대화 시나리오
- 여러 캐릭터가 참여하는 단체 대화
- 음성 입출력
- 캐릭터 표정 또는 상황 이미지 생성
- 인기 캐릭터와 대화 유지율 통계
- 유료 메시지 또는 작가 수익 배분

## 17. 구현 전 최종 결정이 필요한 항목

- 일일 무료 메시지 수
- 대화 기록 보관 기간
- 미성년자 및 성인 콘텐츠 정책
- 캐릭터 챗봇 설정에 별도 승인 절차를 둘지 여부
- 작품 완결 또는 공개 중단 시 기존 대화를 계속 허용할지 여부
- 캐릭터 설정 업데이트를 기존 대화에 적용할 수 있는 선택지를 제공할지 여부
